## 0. 速览：UI 设计的"五大阶段 + 五大工件"

| 阶段 | 工件（产出物） | 决策尺度 | 验证手段 |
|---|---|---|---|
| 1. 战略对齐 | **PRD / 简报** | 为什么做、给谁做、衡量什么 | 干系人走查 |
| 2. 信息架构 | **站点地图 / 用户流程图** | 走什么路径看到什么 | 走查流程 |
| 3. 低保真 | **Wireframe（线框稿 / 底稿）** | 放不放、放哪儿、大小 | 内容可读性 |
| 4. 设计图稿 | **Mockup（视觉稿）** | 字号、颜色、间距、品牌 | 像素对齐、对比度 |
| 5. 高保真原型 | **Prototype（可交互原型）** | 点了会怎样、动画怎样 | 用户测试 |

> "基础五件套"是 UI 设计的支柱；任何花式技法都从这里生长。

## 1. 第一性原理：UI 设计到底解决什么问题

UI 设计 = **让人用最少力气、获得最准信心的界面**。

这个问题可以被拆成三个相互独立的基本子问题：

```
子问题一：信息要传达什么？       → 内容层（信息架构 / 文案）
子问题二：传达的次序和结构是什么？→ 结构层（流程 / 导航 / 层级）
子问题三：用什么感官呈现最有效？  → 表现层（视觉 / 交互 / 动效）
```

> 第一性原理：你看到的任何 UI，都是这三个子问题的答案在不同层级上的层层递进。  
> 设计师的工作就是**反复在三层之间来回切换、消除矛盾**。  
> 工程师的工作是把这三层**翻译成机器能理解的代码**。  
> 你的工作是决定**这三层每一层要回答的具体问题**。

## 2. 五大工件详解

### 2.1 PRD / 简报（Product Requirements Document / Brief）

**是什么**  
项目开始前的"我们要做什么、为什么、给谁"的白纸黑字。是对齐**干系人**的文档。

**为什么要做这一步**  
- UI 设计里 80% 的返工来自"理解错目标"。PRD 是最先消歧的工具。
- 没有 PRD，设计师会"猜你想做什么"，且下次再猜一次。

**应该做什么**

| 项 | 写什么 | 谁写 |
|---|---|---|
| 目标 | 业务/产品目标（北极星指标） | 产品 |
| 场景 | 谁、在什么情境下使用 | 产品/UX |
| 核心问题 | 用户痛点是什么、为什么重要 | 产品/UX |
| 验收标准 | 什么叫"做完了"（可量化） | 产品 |
| 范围 | 做哪些、不做哪些 | 产品 |
| 时间 | 节奏、里程碑 | 产品 |

**怎么把它做好**

- **每段不要超过两屏可读**——PRD 越长、共识越少。
- 用**用户故事**（As a [user], I want to [action], so that [benefit]）而非工程师语义。
- 引用、可衡量的指标必须明确（"提高 30% 转化"比"提升体验"好）。

**做好的标准**

- 任何干系人读完后能答出 3 件事："给谁用、用来做什么、用完得到什么"。
- 没有"应该、可能、大概"——所有值都明确或明确"暂时未知"。

**对照常见错误**：PRD 一上来就写"UI 要有动画"——这是**实现细节**，不是 PRD。

---

### 2.2 信息架构 / 用户流程（IA / User Flow）

**是什么**  
把"用户从进来到达成目标"切成步骤，把每步里用户需要的**信息项**列清楚。常表现为：站点地图、任务流程图。

**为什么需要**  
- UI 不只是"好看"，是"让人走完流程"。流程有缺陷，UI 再漂亮也救不回来。
- 信息架构错了，后期改的成本是 10×——因为每个页面都受影响。

**应该做什么**

1. 列出所有目标用户的**核心任务**（用户旅程 maps）
2. 对每个任务，拆分步骤：每个步骤用户**输入什么、看到什么、思考什么**
3. 用方块图、流程图、文字描述都行，重在**结构**而非美观
4. 标出**异常分支**：出错怎么办、找不到怎么办、超时怎么办

**怎么把它做好**

- 每条任务流的步骤**不超过 7 步**。超过就拆子流程。
- 每个步骤必须有**清晰的退出条件**（完成 / 失败 / 放弃）。
- 关键决定点做**分支**：是/否、登录/不登录、新手/老手。

**做好的标准**

- 任何人拿这张图，能立刻照着做出"对的"UI（不一定好看，但不会漏）。
- 边缘情况（断网、空白页、错误）都画到了。

> 第一性原理：信息架构决定 UI 的"骨架"，骨架对了才有肌肉和皮肤。

---

### 2.3 低保真线框稿 / Wireframe（底稿）

**是什么**  
把流程图里的每一步**具体化成一张具体的页面布局**：方块 + 占位文字。黑白灰、随便画、不上颜色字体。

**为什么需要**  
- 与"信息架构"不同——架构是"流程"，线框稿是"一屏放什么"。
- 黑白稿的好处：**逼所有人讨论内容、不讨论美观**——早期就把内容塞错的问题揪出来。

**应该做什么**

- 一屏一页纸，先主体、后次要
- 标注每个区块的内容来源、占位字符数（"此处 20 字标题，8 字正文"）
- 标注交互状态：默认 / hover / 选中 / 禁用 / 错误

**怎么把它做好**

- **铅笔草图 > 软件原型**：越早期越应该快、能丢
- 保持同一模板字号、灰度，越一致越可比
- 不要"美化"——任何颜色、明暗、阴影都意味着"已经在设计视觉"了，那时别请人评内容

**做好的标准**

- 用户能在 5 秒内指出"我要做的事在不在这里"
- 信息层级一眼就分得清（主标题比次标题大、按钮比段落抢眼）
- 没有装饰、没有品牌字体、所有元素可重排

---

### 2.4 设计图稿 / Mockup

**是什么**  
线框稿的"上色版"——填入真实文字、字体、颜色、图片、品牌调性。是给开发"照着做"的**最终视觉规范**。

**为什么需要**

- 视觉一致性由"一次决定、所有页面一样用"换来
- 设计师对每个像素（字号、间距、颜色）都深思过，不是"差不多就好"

**应该做什么**

- **设计系统先于单页设计**：先确定色板、字号阶、间距阶、组件库（按钮、卡片、表单）。这就是 §3 的内容。
- 把所有线框稿的页面用真实素材填满
- 把 hover / active / disabled / error / loading 各种态都画出来
- 移动端 / 桌面端 / 平板分别画

**怎么把它做好**

- 8 点网格 / 4 点网格——所有间距都是 4 或 8 的倍数
- 字号阶 → 4–6 个常见值（如 12/14/16/20/24/32）
- 颜色 → **主色 / 中性色 / 状态色** 三组，每组 8–10 个梯度
- 间距节奏 → 4/8/12/16/24/32/48/64 px（数值是阶梯的，不是连续的）
- 留白 > 装饰：宁可空着也别塞

**做好的标准**

- 把图稿随机抽一帧，**只看 1 秒能识别"这是什么页面、给谁、主要动作是什么"**
- 文字层级清晰，一眼能数出 1/2/3 三个层级
- 颜色不超过 5 个主色（在视觉上可数）
- 对比度满足 WCAG AA（正文 4.5:1，大字 3:1）
- 同一组件（按钮）在所有页里**看起来和操作方式完全一样**

---

### 2.5 高保真原型 / Prototype

**是什么**  
设计图稿"动起来"——点了能跳、表单能填、动效按节奏演。

**为什么需要**

- 静态图无法传达"流畅感"、"操作反馈"、"动画节奏"
- 用户测试时没有交互，看不出"卡不卡、找得到吗"
- A/B 测试在原型阶段更便宜——比上线后改便宜 100×

**应该做什么**

- 链接所有可交互元素 → 目标状态/页面
- 微交互：按钮按下、列表展开、loading 出现、toast 消失
- 真实内容占位（接近上线的图文数据）

**怎么把它做好**

- **动效要有"目的"**——推动用户视线 / 表达因果 / 维持上下文。例如"上级菜单滑出，下级滑入" 表层级；"Toast 弹出再收回" 表反馈。
- 动效时长 200–500ms（200ms 以下不察觉、500ms 以上让人烦躁）
- 缓动用 ease-out（开始快、结束慢），少用 linear（机械感强）

**做好的标准**

- 用户测试 5 个真人完成核心任务，无提示也能走完
- 性能不卡（移动端 60fps）
- 真实使用场景（小屏、暗光、单手）都能用

## 3. 设计系统（Design System）：贯穿始终的横向资源

> 不是"一个阶段"，而是**对前五件套的复用抽象**。没有它，单页越漂亮越不可持续。

### 3.1 三大子系统

| 子系统 | 内容 | 你跟设计师沟通用的词 |
|---|---|---|
| **设计令牌（Design Tokens）** | 原子：颜色 / 字号 / 间距 / 圆角 / 阴影 / 动画时长 | "用 --primary-500"、"字号用 --text-md"、"间距 --space-4" |
| **组件库（Components）** | 分子：按钮 / 输入框 / 卡片 / 弹窗 / 导航 / 表格 | "用 Button/Primary"、"弹窗用 Modal/Small" |
| **模式库（Patterns）** | 复合体：登录页 / 注册流 / 空状态 / 错误页 | "用 EmptyState/Light"、"ErrorPage/Retry" |

### 3.2 三类用户的语言

> 设计系统的"自顶向下三个层级"，对应**业务、设计、技术**三种干系人：

| 层级 | 名称 | 业务看的 | 设计看的 | 技术看的 |
|---|---|---|---|---|
| **愿景** | Vision / Principles | 这套系统服务于什么理念 | 设计原则 / 价值观 | 设计令牌的根本原因 |
| **系统** | System / Tokens | 主色是什么、字号多大 | 设计令牌、组件规范 | CSS 变量 / JSON tokens |
| **部件** | Components / Patterns | 典型页面长啥样 | 组件库 | 组件代码库 |

### 3.3 为什么"先有令牌、再有组件"

> 第一性：令牌是"不可违反的常量"。  
> 写组件前未定色板——反复改色 = 写错一次、反复改。  
> 反过来：先定令牌，所有组件拉满规范。后期改色只动一处。

## 4. 角色与协作流（你身边的协作地图）

| 角色 | 关注什么 |
|---|---|
| **产品（PM）** | PRD、用户流程、验收标准 |
| **UX（交互设计师 / 用户体验）** | 信息架构、用户研究、原型 |
| **UI（视觉设计师 / 用户界面）** | 设计图稿、设计系统、品牌一致性 |
| **前端工程师** | 把设计图稿 / 设计令牌 / 组件库变成代码 |
| **后端工程师** | 数据怎么存、接口怎么定、状态怎么管理 |
| **QA** | 按验收标准（PRD + 设计图）走查 |
| **你自己** | 决策点：何时从一阶段进到下一阶段、投入多少时间 |

> **协作的第一性原理**：每个阶段交付一个"足够明确、可被下游核对"的产物，团队就能无歧义推进。

## 5. 关键的"决策时机"与"门控"

### 5.1 设计流程的"四个门"

```
门 1：PRD 签字 → 门 2：流程图签字 → 门 3：线框稿签字 → 门 4：设计图稿签字 →（开发）→ 门 5：原型签字 →（上线）→ 门 6：上线复盘
                                                                                              ↑                    ↑
                                                                                         用户测试通过          验收对版
```

> 每个门 = "我看过、我同意、可以往下"——文档化、可回溯。

### 5.2 何时该停、何时该进

| 决策 | 进的条件 | 停的危险 |
|---|---|---|
| 进入流程图 | PRD 已签字 | 在没明确"用户是谁"的情况下画页面 |
| 进入线框稿 | 流程图已被认可 | 在没确认每步内容来源的情况下定布局 |
| 进入设计图稿 | 线框稿内容已可读 | 内容还在变，就上"漂亮外观" |
| 进入原型 | 设计图稿已评审 | 没图稿时直接做原型会反复推翻 |
| 进入开发 | 原型通过用户测试 | 视觉与流程仍争议，进了开发会扯皮 |

**第一性**：**早期错误是最便宜的**。

- PRD 阶段改 1 个概念 → 1 小时、0 损失
- 流程图阶段改 1 个步骤 → 1 天、几张稿重画
- 线框稿阶段改 1 个布局 → 几天、几张稿 + 流程 + PRD
- 设计图稿阶段改 1 个组件 → 1 周、影响所有页
- 原型阶段改 1 个交互 → 1 周、要重测
- 上线后改 1 个流程 → 1 月、数据丢失风险

## 6. UI 设计的"硬指标"（用来评判"做好没"）

### 6.1 可用性（Usability）—— 5 大原则

Nielsen 1993 年的 5 大可用性原则，至今是黄金标准：

| 原则 | 第一性原理 | 实战翻译 |
|---|---|---|
| **可见性**（Visibility） | 状态可见 | "我现在在哪、能去哪"必须能看见 |
| **匹配真实世界**（Match） | 系统说人话 | 文案用用户语言而非工程师语言 |
| **可控**（User Control） | 用户能 undo | 能返回、能取消、能撤销 |
| **一致**（Consistency） | 同一件事同一做法 | 颜色统一、字号统一、组件行为统一 |
| **预防错误**（Error Prevention） | 让错不发生 | 危险操作二次确认、错误输入预先提示 |

### 6.2 可访问性（Accessibility / a11y）—— WCAG 4 大原则

| 原则 | 释义 | 量化标准 |
|---|---|---|
| 可感知 | 信息可被任何感官获取 | 对比度 4.5:1 (AA)、3:1 (大字体 AA) |
| 可操作 | 键盘、鼠标、触屏都能用 | Tab 顺序、所有点击元素有焦点态 |
| 可理解 | 文案、操作意图清晰 | 阅读等级 6–8 年级（英文）/对应中文 |
| 鲁棒 | 屏幕阅读器能读 | aria-label、role、语义化标签 |

> 当你看到"我们得考虑老年用户"——这叫 a11y；当你的 PM 说"做个无障碍版"——这是 ROI 最高的几小时投入之一。

### 6.3 视觉设计硬指标

| 维度 | 标准 |
|---|---|
| 对比度 | 文字 vs 背景 ≥ 4.5:1 (AA) |
| 字号阶 | 不超过 6 个常用字号 |
| 间距阶 | 8 点网格 / 4 点网格 |
| 颜色 | 主色 ≤ 5 个、中性色 ≤ 8 个梯度 |
| 触控目标 | ≥ 44 × 44 px (Apple HIG) / 48 × 48 px (Material) |
| 加载时间 | 首次 < 3s；交互 < 100ms |

## 7. UI 设计常见误区（务必避免）

| 误区 | 真实成本 | 替代做法 |
|---|---|---|
| "一上来就画漂亮图" | 内容错乱、后期大改 | 先 PRD → 流程 → 线框 → 视觉 |
| "每个页面都不同" | 用户学不会、品牌散 | 设计系统先于单页 |
| "用装饰表达功能" | 用户分不清主次 | 内容驱动视觉 |
| "动画越多越高级" | 拖慢、分散注意力 | 动画为因果服务，不为炫技 |
| "按颜色区分状态" | 色盲用户分不清 | 颜色 + 图标 + 文案 三冗余 |
| "首创词汇" | 用户找不到东西 | 借用成熟产品的语言 |
| "字体越多越有风格" | 杂乱、性能差 | 一个英文字体 + 一个中文字体 |

## 8. 你应该怎样跟 AI / 设计师对话

> 这是作为外行最实用的一节——学会这几条，能让你跟任何协作方沟通效率翻倍。

### 8.1 用"工件 + 维度 + 决策"的方式提问

| 错误示例 | 正确示例 |
|---|---|
| "改一下登录页" | "改 act-3 那页的 kicker 字号从 11px 到 14px，配色用 var(--primary)" |
| "做得漂亮点" | "字号层次再加一档（11/14/16/20/24/32），主色保留但背景用 5% 黑过度" |
| "加点动效" | "按钮 hover 时背景色 200ms ease-out 渐变，不放大不变形" |
| "跟那个 app 一样" | "主色调用 #FF6B35（橙色）；卡片圆角 12px；留白节奏 8 点网格" |

### 8.2 沟通模板：SMART 询问

```
S - Stage（我在哪个阶段？这里是线框稿阶段）
M - Metric（怎么判断改好了？字号层次 6 个梯度可数）
A - Action（具体改什么？把 h2 从 32 缩到 28）
R - Reason（为什么改？因为 RCT3 与 RCT4 视觉重量失衡）
T - Time（什么时候改完？下一轮迭代）
```

### 8.3 报错 / 反馈的标准格式

```
【产品 / 文件 / 位置】：3d-hero.html / RCT3 段落 / 正文 18px 字号
【现状】：RCT3 正文比 RCT2 大 4px，视觉重量失衡
【期望】：所有正文用 18px（统一）
【验收】：16:9 视口下截屏，对比 RCT3 与 RCT2 正文视觉重量一致
```

## 9. 进阶：UI 设计的"现代分化"

| 流派 | 关注 | 工具 |
|---|---|---|
| **信息架构** | 内容组织 | 卡片分类、流程图 |
| **交互设计** | 行为 / 反馈 | 动效、原型、用户研究 |
| **视觉设计** | 美学 / 品牌 | 字体、颜色、栅格 |
| **无障碍设计** | 包容性 | WCAG、屏幕阅读器、a11y 测试 |
| **设计系统** | 可规模化 | Token、Storybook、文档站 |
| **设计运营** | 跨团队一致性 | 设计审稿、设计 lint |

> 第一性：UI 设计是个**多工种学科**——同一项目可能同时存在 6 个人做着 6 件不同的事，但他们说的是同一套语言。

---

## 10. 一个"理想 UI 项目"的最小流程（14 步）

```
1. 需求（PM 写 PRD）              — 1–2 天
2. 用户研究（UX 走访 5 个用户）     — 1 周
3. 信息架构（UX 出 IA 流程图）      — 2–3 天
4. 线框稿（UI 出黑白底稿）          — 3–5 天
5. 内部评审（所有干系人）            — 半天
6. 设计系统（UI 建 token + 组件）   — 3–5 天
7. 高保真图稿（UI 套用系统填图）     — 1 周
8. 设计评审（PM + UI + 前端）       — 半天
9. 原型交互（UI 加点击跳转）        — 1 周
10. 用户测试（UX 找 5 人走流程）    — 1 周
11. 设计交付（出 Zeplin/Figma spec）— 1 天
12. 开发实现（前端 1:1 复刻）       — 2–4 周
13. QA 走查（按 PRD + 设计图对版）  — 1 周
14. 上线 + 复盘                    — 1 天 + 1 周后回顾
```

> 这是"成熟团队"的标准节奏——有些项目可以压缩到 4 步（PRD → 线框 → 设计 → 上线），但**门控不能省**（PRD 走查、图稿评审、对版 QA）。

## 11. 你专属的"速查清单"（贴在工作台随时用）

### 11.1 让我（AI）改图时，给我这 4 件套

```
A. 哪个页 / 哪段内容（act-3 / kicker / 标题）
B. 改什么属性（字号 / 颜色 / 间距 / 位置 / 节奏）
C. 从什么值到什么值（11px → 14px）
D. 验收标准（截屏对比 / 数值核对）
```

### 11.2 看一份图稿时，按这个顺序问

1. 这是**哪个阶段**的产物？（PRD / 流程 / 线框 / 图稿 / 原型？）
2. 它的**用户目标**是什么？（看 PRD 还是猜）
3. 主要行动按钮 / 信息 / 文字层级清不清楚？
4. 颜色、字体、间距遵循同一套规范吗？
5. 异常状态（loading / error / empty）有没有？

### 11.3 跟设计师 / 工程师沟通的黄金句

- "这是我看到的、这是我想要的、衡量好不好的标准是 X"
- "这个改动对**用户价值**有什么帮助"
- "如果只能选一个，你建议先做哪个？"
- "这个改动的成本是多少？和它带来的收益匹配吗？"

## 12. 收尾：第一性原理再总结

UI 设计的本质：

> **帮用户以最低代价，在正确的时间，得到正确的信息，做出正确的决定。**

每个工件、每个步骤、每个原则，最终都服务于这一句话。  
当你和设计师/AI 协作卡住时，回到这一句话——你们就回到同一频道了。
